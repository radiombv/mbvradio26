# MBV

## Digital Platform & Website Design Brief

### MBV | 24/7 Classic Jungle Radio

---

# 01 — PROJECT OVERVIEW

MBV is an independent online radio station originally founded by DJ **Vaxla**, associated with Pennsylvania and classic jungle / drum & bass culture.

The project is being rebuilt as a modern digital radio experience while preserving the original MBV identity, particularly its original logo and underlying character.

The new platform should include:

* A modern responsive website
* Progressive Web App (PWA) functionality
* A dedicated desktop executable
* Continuous 24/7 automated broadcasting
* Occasional live programming
* Live track/program information
* Schedule and recently played information
* Listener requests
* Persistent playback while navigating
* A clear historical/about section
* Future physical merchandise, beginning with an MBV sticker

The central objective is **not to modernize MBV into a generic internet-radio website**.

The objective is to make MBV feel like the station it always could have been if it had been designed for 2026.

---

# 02 — THE CORE IDEA

MBV should feel like a **digital radio receiver**.

The strongest conceptual test is:

> **“What the hell is this? This feels like a car radio.”**

Not literally a car-radio simulator.

No fake dashboard.
No knobs everywhere.
No skeuomorphic interface.

Instead, the website should inherit the behavioral qualities of a good physical receiver:

* Immediate
* Obvious
* Persistent
* Low cognitive load
* One dominant function
* Strong state indication
* Physical confidence
* Designed to be left running
* Easy to operate without looking at it constantly

The user should be able to open MBV, understand its state within approximately five seconds, press play, and leave it running.

The site is fundamentally **a receiver, not a content portal**.

MBV must feel:

* Independent

* Cool
* Physical
* Slightly underground
* American without advertising its Americanness
* Rooted in classic jungle / D&B culture
* Contemporary

* Distinctive
* Like it has existed somewhere outside the mainstream

It must **not** feel:

* Corporate
* Like Spotify

* Like BBC Radio
* Like a generic internet-radio template
* Like an EDM nightclub
* Like a gaming website
* Like a crypto/AI startup

* Like a nostalgia website
* Like a memorial project
* Like a 1990s web parody
* Like a GTA clone
* Like a NASCAR fan site

The site should feel **real, cool as hell, and like somewhere**.

# 04 — CULTURAL REFERENCE POINTS

The emotional references behind MBV include:

* 1990s NYC project blocks
* GTA-era underground radio
* Pennsylvania mountain roads at night
* Vintage American auto repair garages
* Aftermarket automotive stickers
* Rustbelt towns
* Night driving
* Machines
* Independent projects
* Physical music culture
* Classic jungle / drum & bass

These are **emotional and cultural references, not literal visual instructions**.

Do not decorate the website with:

* Racing flags
* Flames
* Fake sponsor decals
* Checkered patterns
* Car photography
* GTA graphics
* Fake 1990s UI
* Excessive grunge

The correct principle is:

> **Brand density, not visual density.**

The identity can be rich.
The interface must remain sparse.

---

# 05 — HISTORICAL PRINCIPLE

MBV does not imitate the past.

> **MBV operates in the present with the memory of the past embedded within.**

The original identity should be preserved rather than recreated.

The site should pay homage to 1990s jungle culture without becoming a 1990s-themed website.

The original MBV logo is **untouched**.

It is the actual logo used by the new site.

The new system is built around it rather than replacing or redesigning it.

# 06 — VISUAL IDENTITY

## Canonical colors

### Background

`#121212`

### Primary accent

`#f8ca07`

### Secondary

White

### Legacy

Dark green

Dark green is **not** a primary current brand color.

# 07 — YELLOW SEMANTICS

Yellow should mean something.

Use `#f8ca07` primarily for:

* Active navigation
* LIVE state
* Selected states
* Current schedule position
* Important signal information
* Primary emphasis
* System feedback

Do not flood the interface with yellow.

Yellow should communicate:

> **active / signal / current**

---

# 08 — TYPOGRAPHY

The typographic system combines:

### A — Contemporary grotesk

For primary UI and readable content.

### E — Condensed display / utilitarian typography

For:

* Program titles
* Time information
* Station identifiers
* Certain large labels
* Technical micro-information

A monospace/technical face may be used sparingly for system information.

The overall typography should be:

* Clean
* Contemporary
* Highly legible
* Slightly industrial
* Restrained

Avoid typography that makes the website look retro.

---

# 09 — IMAGERY

**No photography.**

The site may use:

* MBV logo assets
* Track artwork
* Physical merchandise imagery where necessary

Track artwork comes from the broadcast system.

Photography should not be used to manufacture an atmosphere that the interface can create itself.

---

# 10 — TEXTURE

Default MBV should have **no obvious visible texture**.

The Standard skin should be extremely clean.

Potential future skins may introduce subtle material/atmospheric qualities, but they must never interfere with usability.

---

# 11 — MOTION

Motion exists only when it communicates something.

> **Things move with purpose, but minimally.**

No gratuitous animations.

No constant background motion.

No decorative particles.

No excessive transitions.

Animations should communicate:

* State changes
* Track changes
* Playback
* Buffering
* Navigation
* System feedback

---

# 12 — SKINS

The platform may eventually support multiple visual skins.

## STANDARD — canonical

* `#121212`
* `#f8ca07`
* White
* No visible texture
* Minimal motion

## NIGHT

More atmospheric while retaining the same information architecture and usability.

## SHOP

Industrial/material-inspired treatment intended for commercial/physical-product contexts.

Skins must **never compromise usability**.

Standard remains the canonical MBV experience.

---

# 13 — BOOT EXPERIENCE

The first interaction should feel ceremonial without becoming nostalgic.

Sequence:

> **MBV LOGO**
>
> **TURN ON**
>
> **LIVE**

The yellow original MBV logo is used.

No green transition.

No CRT effects.

No scanlines.

No VHS effects.

No fake PlayStation graphics.

The conceptual reference is a **power-on ritual**, not retro visual emulation.

The first visit can have a stronger boot experience.

Returning sessions may eventually support a quieter/immediate entry into LIVE.

---

# 14 — PRIMARY NAVIGATION

The entire platform has three primary destinations:

> **LIVE / SCHEDULE / ABOUT**

There is no separate MUSIC section.

Music information belongs to the receiver and Schedule.

Navigation should be quiet and persistent.

The active section uses yellow.

The site should never feel like a conventional content website with a large corporate header.

On LIVE, the receiver itself effectively **is the page**.

---

# 15 — LIVE

LIVE is the primary experience.

The five-second comprehension test:

A user should immediately understand:

1. This is MBV
2. The station is live/connected
3. What program is currently playing
4. What track is playing
5. How to control it

---

## LIVE hierarchy

Recommended order:

**MBV**

**● LIVE**

**PROGRAM NAME**

**ARTIST**

**TRACK TITLE**

Artwork

Playback controls

Secondary controls

---

# 16 — ARTWORK

Track artwork is displayed as a **spinning circle**, rather than a square image clipped into a circle.

Desktop target:

Approximately **220–260px**

Mobile target:

Approximately **180–210px**

Artwork should be visually meaningful but must not overpower the MBV identity.

The composition should balance:

* Artwork
* Metadata
* Negative space

---

# 17 — ARTWORK ROTATION STATES

Artwork rotation is semantic.

### PLAYING

Constant rotation.

### PAUSED

Rotation stops exactly where it is.

### MUTED

Rotation continues.

### BUFFERING

Rotation stops / enters a distinct buffering state.

### DISCONNECTED / OFFLINE

Rotation stops.

This is not decoration.

The artwork behaves as a visual indicator of the receiver state.

---

# 18 — TRACK CHANGES

When the track changes:

* Artwork changes
* Artist changes
* Title changes

These should transition together.

Recommended transition:

**250–400ms**

The music player itself should remain stable.

A show/program change should update quietly without unnecessarily resetting the player.

---

# 19 — SIGNAL TRUTH

The interface must always tell the truth about the broadcast.

Required states include:

### LOADING

`CONNECTING`

### READY

`PLAY`

### BUFFERING

`BUFFERING`

### LIVE

`● LIVE`

### PAUSED

`PAUSED`

### OFFLINE

`MBV IS CURRENTLY OFFLINE`

### CONNECTION LOST

Explicit connection-lost state.

### RECONNECTING

`RECONNECTING…`

There must never be:

* A fake spinning record while the stream is dead
* A LIVE indicator when disconnected
* Stale metadata presented as current
* Fake playback state

Core principle:

> **The interface always tells the truth about the signal.**

---

# 20 — PLAYBACK CONTROLS

Primary control:

**PLAY / PAUSE**

Secondary controls:

* Volume
* Mute
* Requests

The play/pause control should be the most visually prominent interactive element.

---

# 21 — KEYBOARD CONTROLS

Desktop:

`SPACE` — PLAY / PAUSE

`M` — MUTE

`↑ ↓` — VOLUME

`← →` — UI NAVIGATION

Keyboard controls must not interfere with text entry.

When a keyboard action occurs, temporary centered OSD feedback appears near the receiver.

Examples:

> `VOLUME 84%`

> `MUTED`

> `PLAY`

> `PAUSED`

The OSD should briefly appear and fade.

It should not behave like a generic corner notification.

---

# 22 — AZURACAST

AzuraCast is the planned broadcast/source-of-truth system.

The website should use the broadcast system for:

* Stream state
* Artist
* Track
* Current program/show
* Artwork
* Recently played tracks
* Schedule information where applicable

The previous MBV architecture already used a now-playing API approach.

That concept should be retained and modernized rather than discarded.

The implementation should be designed so that **AzuraCast remains authoritative**.

---

# 23 — SCHEDULE

Schedule is not a conventional calendar.

It is a representation of **MBV's broadcast day**.

The primary object is a continuous 24-hour broadcast timeline.

The user should understand:

> **Where are we in MBV's day?**

---

# 24 — DAYPARTS

The broadcast day is divided into approximately 4–5 parts.

Known programming:

**03:00–07:00 — CHILLOUT**

**21:00–03:00 — NIGHT DRIVE**

The remaining dayparts are still to be finalized:

**07:00–12:00**

**12:00–18:00**

**18:00–21:00**

Each daypart will have:

* A show/state name
* Time range
* Simple icon
* Short description
* Automated/live designation

Icons should function as an MBV broadcast-state language.

Examples may include:

* Sun
* Cloud
* Moon

But they should be treated as simple symbols rather than emoji or weather-app graphics.

They describe **state of day / state of mind**, not genre.

---

# 25 — SCHEDULE TIMELINE

Timeline anchors:

* 00
* 03
* 07
* 12
* 18
* 21
* 24

Blocks should be proportional to their actual duration.

The current position is represented by:

> **A yellow vertical line**

The line moves continuously with real time.

Avoid a giant NOW badge.

The line itself is the signal.

A small label may identify it if necessary.

---

# 26 — EXPANDING DAYPARTS

Clicking/tapping a daypart expands its information in place.

Example:

> `☾ NIGHT DRIVE`
>
> `21:00 — 03:00`
>
> Short description.
>
> `AUTOMATED BROADCAST`

Expansion should be concise.

Do not turn each daypart into a long editorial card.

---

# 27 — RECENTLY PLAYED

Seven recently played tracks appear underneath the Schedule.

This should be:

**one clean list**

not:

* Seven album cards
* A Spotify-style grid
* A music discovery interface

Artwork can be included in restrained form if useful.

The section exists primarily to answer:

> **What has MBV been playing?**

---

# 28 — FLOATING RECEIVER

When browsing Schedule, playback remains available through a **small floating receiver**.

It should include, where space allows:

* Signal state
* Small artwork
* Artist
* Track
* Play/pause
* Volume
* Request access

It should feel like a piece of the receiver that remains with the user.

When the user returns to LIVE, the receiver becomes the primary full-page experience again.

---

# 29 — MOBILE SCHEDULE

Mobile Schedule should be **horizontally scrollable**.

The initial position should place:

> **NOW**

at the center of the viewport.

Users can drag through the broadcast day.

Do not compress the entire 24-hour schedule into an unreadable vertical mobile list.

Do not turn it into a conventional calendar.

The Schedule should remain a **live timeline**.

# 38 — PWA

The mobile experience should be treated as a genuine **PWA**, not merely a responsive webpage.

The experience should support:

* Installation
* Persistent application identity
* Appropriate app icon
* Fast startup
* Full-screen/standalone presentation where supported
* Persistent playback where technically/platform permitted
* Receiver-first interaction
* Responsive Schedule
* Touch-friendly controls

The mobile experience should retain the same receiver philosophy as desktop.

---

# 39 — DESKTOP APPLICATION

The desktop version should be a **dedicated executable**, not simply an Electron wrapper around the website.

It should behave like a compact MBV receiver.

Core capabilities:

* Stream playback
* Track/program information
* Artwork
* Playback controls
* Volume/mute
* Requests
* Connection state
* Persistent operation
* Native-feeling desktop behavior

The desktop and PWA experiences can share the same underlying receiver logic and backend services.

# 42 — DAYPART CONCEPT

Programming is not simply divided by genre.

The dayparts represent **states of mind**.

### CHILLOUT

03:00–07:00

Late-night / early-morning decompression.

### NIGHT DRIVE

21:00–03:00

High-energy night driving as a state of mind:

* Empty highways
* Mountain roads
* Rain or dry pavement
* High-octane D&B
* Gas stations
* Energy drinks
* Motor oil
* Cool air
* Freedom
* Movement toward nowhere in particular

This should **not** be represented literally through photography or automotive decoration.

The feeling should emerge from programming, naming, pacing and interface behavior.

---

# 43 — DESIGN PRINCIPLE

The strongest design rule is:

> **MBV does not imitate the past. It operates in the present with the memory of the past embedded within.**

A second rule:

> **Brand density, not visual density.**

A third:

> **The interface always tells the truth about the signal.**

And the ultimate experiential test:

> **At 1:47 AM, opening MBV should feel like turning on a radio, not visiting a website.**

---

# 44 — WHAT THE DEVELOPER SHOULD NOT DO

Do not turn MBV into:

* A generic radio CMS
* A streaming-service clone
* A music discovery platform
* A magazine
* A blog
* A social network
* A podcast platform
* A nightclub website
* A retro website
* A car-themed novelty website
* A memorial website
* A merchandise-first brand
* A dashboard overloaded with statistics

Do not add interface elements simply because modern websites normally have them.

Every component should justify its existence.

---

# 45 — TECHNICAL LEGACY

The original MBV website was extremely simple:

> Logo → player → footer

It contained:

* MBV branding
* Stream player
* Artist/title
* Show information
* Artwork
* Play/pause
* Volume
* Requests
* Contact
* Internet radio identification

The new platform should **preserve the functional DNA** of that experience while rebuilding the implementation.

Legacy technical issues include:

* HTTP resources
* Legacy JavaScript/jQuery
* External Google Fonts
* Font Awesome dependency
* Legacy radio API implementation
* Weak responsive CSS
* Old metadata handling

These should not be carried forward merely for nostalgia.

The new implementation should be modern, performant, accessible and maintainable.

---

# 46 — DEVELOPMENT PRIORITIES

Priority order should be:

### 1. Receiver reliability

The stream must work.

### 2. Signal truth

The UI must accurately represent connection/playback state.

### 3. Live experience

The current broadcast must be immediately understandable.

### 4. Persistent playback

Navigation must not unnecessarily interrupt listening.

### 5. Schedule

The broadcast day must be understandable at a glance.

### 6. Mobile/PWA

MBV should work as an installed listening application.

### 7. About/history

Concise provenance and documentation.

### 8. Physical identity

Sticker/shop integration.

Visual experimentation should never compromise the first six priorities.

---

# 47 — SUCCESS CRITERIA

The rebuild succeeds if a first-time visitor can:

1. Recognize MBV immediately.
2. Understand that it is a 24/7 classic jungle/D&B station.
3. Know whether the station is actually live/connected.
4. See what is playing.
5. Start listening immediately.
6. Continue listening while navigating.
7. Understand where the station is in its broadcast day.
8. Discover MBV's history without being subjected to a brand essay.
9. Understand that Vaxla founded the station without the website becoming a memorial.
10. Install/use MBV comfortably as a mobile or desktop receiver.
11. Encounter the MBV physical identity and potentially obtain a sticker.
12. Leave with the feeling that they discovered **a real station**, not a website template.

---

# 48 — FINAL CREATIVE DIRECTION

MBV should feel like something you **found**.

Not something a marketing department launched.

Not something pretending to be underground.

Not something recreating a decade.

It is a contemporary independent radio station with an existing identity, a real history, a specific musical purpose and a physical personality.

The interface should therefore be confident enough to stay quiet.

**Open it.**

**Turn it on.**

**See what's playing.**

**Listen.**

**Leave it running.**
